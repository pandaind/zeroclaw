## 1. The Config File

ZeroClaw is configured with a TOML file (typically `~/.config/zeroclaw/config.toml`).

```toml
# config.toml example
[agent]
name = "my-agent"
provider = "anthropic"
model = "claude-opus-4-5"
system_prompt = "You are a helpful assistant."

[providers.anthropic.default]
# api_key is stored encrypted — use `zeroclaw config set-secret`
api_key = ""

[channels.telegram.my-bot]
enabled = true
allowed_users = ["alice", "bob"]
# bot_token is stored encrypted

[security]
autonomy = "supervised"
workspace = "/home/alice/agent-workspace"

[memory]
backend = "sqlite"
```

**Why TOML?** TOML is human-editable, supports comments (unlike JSON), and
has a well-defined table and array syntax. It is the standard format for Rust
configuration (Cargo uses it, too).

## 2. Config Loading Pipeline

```
1. Determine config file path
   └── directories crate → OS-appropriate path
       macOS:   ~/Library/Application Support/zeroclaw/config.toml
       Linux:   ~/.config/zeroclaw/config.toml
       Windows: %APPDATA%\zeroclaw\config.toml

2. Read and parse TOML
   └── toml crate → deserialise into Config struct

3. Apply environment variable overrides
   └── zeroclaw_config::env_overrides
       ZEROCLAW_PROVIDER → config.agent.provider
       ZEROCLAW_MODEL    → config.agent.model
       ...

4. Decrypt secrets
   └── SecretStore::decrypt_secrets()
       Reads encrypted values from SecretStore
       Injects plaintext into config fields marked #[secret]

5. Validate
   └── zeroclaw_config::validation_warnings
       Checks for missing required fields
       Emits warnings for deprecated keys
       Returns list of ValidationWarning

6. Wrap in Arc<RwLock<Config>>
   └── Allows live patching and concurrent reads
```

## 3. The `Config` Struct

The `Config` struct is the canonical representation of the entire
configuration file. It lives in `crates/zeroclaw-config/src/schema.rs`.

```rust
// Simplified structure (actual has many more fields)
#[derive(Debug, Clone, Default, Serialize, Deserialize, Configurable)]
#[prefix = ""]  // root-level prefix
pub struct Config {
    #[serde(default)]
    pub agent: AgentConfig,

    #[serde(default)]
    pub providers: ProvidersConfig,

    #[serde(default)]
    pub channels: ChannelsConfig,

    #[serde(default)]
    pub memory: MemoryConfig,

    #[serde(default)]
    pub security: SecurityConfig,

    #[serde(default)]
    pub observability: ObservabilityConfig,
}
```

Each sub-section is its own struct with `#[derive(Configurable)]`:

```rust
#[derive(Debug, Clone, Default, Serialize, Deserialize, Configurable)]
#[prefix = "agent"]
pub struct AgentConfig {
    pub name: String,
    pub provider: String,
    pub model: String,
    pub system_prompt: Option<String>,
    pub max_tokens: Option<u32>,
    pub temperature: Option<f32>,
}
```

`#[serde(default)]` on fields means: if the key is absent from the TOML, use
`Default::default()` instead of failing to parse. This allows partial configs.

## 4. The `Configurable` Derive Macro — Deep Dive

The `Configurable` derive macro is in `crates/zeroclaw-macros/src/lib.rs`. It
reads struct fields and generates four groups of methods.

### Inputs the macro reads

```rust
#[derive(Configurable)]
#[prefix = "channels.telegram"]   // TOML key path prefix
pub struct TelegramConfig {
    #[serde(default)]
    pub enabled: bool,

    #[secret]                      // ← encrypted at rest
    pub bot_token: String,

    #[secret]
    pub webhook_secret: Option<String>,

    pub room_id: String,

    #[nested]                      // ← delegate to child struct
    pub advanced: AdvancedConfig,
}
```

### Generated methods

**Group 1 — Secret management**

```rust
// Generated by macro
impl TelegramConfig {
    pub fn secret_fields(&self) -> Vec<SecretFieldInfo> {
        vec![
            SecretFieldInfo { name: "channels.telegram.bot-token", ... },
            SecretFieldInfo { name: "channels.telegram.webhook-secret", ... },
        ]
    }

    pub fn set_secret(&mut self, name: &str, value: String) -> Result<()> {
        match name {
            "channels.telegram.bot-token" => { self.bot_token = value; Ok(()) }
            "channels.telegram.webhook-secret" => {
                self.webhook_secret = Some(value);
                Ok(())
            }
            _ => Err(anyhow!("Unknown secret: {name}"))
        }
    }
}
```

**Group 2 — Property access (runtime patching)**

```rust
// Generated by macro
impl TelegramConfig {
    pub fn prop_fields(&self) -> Vec<PropFieldInfo> {
        vec![
            PropFieldInfo { name: "channels.telegram.enabled", kind: PropKind::Bool },
            PropFieldInfo { name: "channels.telegram.room-id", kind: PropKind::String },
            // Note: #[secret] fields are NOT included here (security)
        ]
    }

    pub fn get_prop(&self, name: &str) -> Result<String> {
        match name {
            "channels.telegram.enabled" => Ok(self.enabled.to_string()),
            "channels.telegram.room-id" => Ok(self.room_id.clone()),
            _ if self.advanced.prop_fields().iter().any(|f| f.name == name) => {
                self.advanced.get_prop(name)  // delegate to nested
            }
            _ => Err(anyhow!("Unknown prop: {name}"))
        }
    }

    pub fn set_prop(&mut self, name: &str, value_str: &str) -> Result<()> { ... }
}
```

**Why kebab-case in prop names?** The macro converts `bot_token` (Rust
snake_case) to `bot-token` (TOML kebab-case convention) when generating prop
names. TOML uses hyphens, Rust uses underscores — the macro bridges this.

### How the macro is implemented (simplified)

```rust
// crates/zeroclaw-macros/src/lib.rs (core logic)
#[proc_macro_derive(Configurable, attributes(prefix, secret, nested))]
pub fn derive_configurable(input: TokenStream) -> TokenStream {
    let input = parse_macro_input!(input as DeriveInput);
    let name = &input.ident;  // e.g. TelegramConfig

    // 1. Find #[prefix = "..."] attribute
    let prefix = get_prefix_attr(&input.attrs);

    // 2. Walk fields
    let Data::Struct(data) = &input.data else { panic!("Only structs") };
    let fields = &data.fields;

    let mut secret_match_arms = vec![];
    let mut prop_field_entries = vec![];

    for field in fields.iter() {
        let field_name = field.ident.as_ref().unwrap();
        let prop_key = format!("{}.{}", prefix, to_kebab(field_name));

        if has_secret_attr(field) {
            secret_match_arms.push(quote! {
                #prop_key => { self.#field_name = value; Ok(()) }
            });
        } else if !has_serde_skip(field) && !is_compound_type(&field.ty) {
            prop_field_entries.push(quote! {
                PropFieldInfo { name: #prop_key.into(), kind: detect_kind(&self.#field_name) }
            });
        }
    }

    // 3. Emit generated code
    quote! {
        impl Configurable for #name {
            fn secret_fields(&self) -> Vec<SecretFieldInfo> { ... }
            fn set_secret(&mut self, name: &str, value: String) -> Result<()> {
                match name {
                    #(#secret_match_arms)*
                    _ => Err(...)
                }
            }
            fn prop_fields(&self) -> Vec<PropFieldInfo> {
                vec![ #(#prop_field_entries),* ]
            }
        }
    }.into()
}
```

The `quote!` macro generates Rust token trees. `#variable` interpolates a
variable into the generated code. `#(#items)*` repeats a pattern for each
item in an iterator.

## 5. Secret Management — `SecretStore`

```rust
// crates/zeroclaw-config/src/secrets.rs
pub struct SecretStore {
    path: PathBuf,   // path to the encrypted store file
    key: [u8; 32],  // derived encryption key
}
```

Secrets are stored in a separate file (`~/.config/zeroclaw/secrets`) that is:
- Encrypted with ChaCha20-Poly1305 (authenticated encryption)
- Keyed from a machine-specific secret (or user-provided passphrase)
- Separate from `config.toml` so the config file can be version-controlled

```toml
# Cargo.toml
chacha20poly1305 = "0.10"   # AEAD cipher
```

**Why ChaCha20-Poly1305?**
- More secure than AES-CBC (provides authentication — detects tampering)
- Faster than AES on devices without hardware AES acceleration
- Recommended by modern cryptographic guidelines (NIST, IETF)

### Workflow

```bash
# Operator sets a secret (never in config.toml directly)
zeroclaw config set-secret channels.telegram.bot-token "1234567890:AAF..."

# Under the hood:
# 1. Read SecretStore
# 2. Encrypt the value with ChaCha20-Poly1305
# 3. Store encrypted blob in secrets file
# 4. Store a placeholder in config.toml (empty string or marker)
```

When the agent loads:
1. `Config` is parsed from TOML (all secret fields are empty strings)
2. `SecretStore::decrypt_secrets()` is called
3. The store decrypts each secret and injects it into the `Config`
4. The `Config` now has live plaintext values in memory (never written to disk)

## 6. Environment Variable Overrides

```rust
// crates/zeroclaw-config/src/env_overrides.rs
pub fn apply_env_overrides(config: &mut Config) {
    if let Ok(v) = std::env::var("ZEROCLAW_PROVIDER") {
        config.agent.provider = v;
    }
    if let Ok(v) = std::env::var("ZEROCLAW_MODEL") {
        config.agent.model = v;
    }
    if let Ok(v) = std::env::var("ZEROCLAW_API_KEY") {
        // Applies to the configured provider
        config.set_secret(&format!("providers.{}.default.api-key",
            config.agent.provider), v).ok();
    }
    // ...
}
```

This is the 12-factor app pattern: environment variables override file config.
Useful for Docker/Kubernetes deployments where secrets come from env vars.

## 7. Live Config Patching

The gateway API allows operators to change config at runtime without restarting:

```bash
# CLI command (uses the gateway HTTP API)
zeroclaw config set agent.temperature 0.7
```

This:
1. Finds the gateway's HTTP endpoint
2. Sends `PATCH /api/config` with `{ "path": "agent.temperature", "value": "0.7" }`
3. Gateway calls `config.write().set_prop("agent.temperature", "0.7")`
4. The `Arc<RwLock<Config>>` means all readers see the updated value immediately

```rust
// Gateway handler (simplified)
async fn patch_config(
    config: Arc<RwLock<Config>>,
    path: &str,
    value: &str,
) -> Result<()> {
    config.write().set_prop(path, value)?;   // calls macro-generated method
    save_config_to_disk(&config.read()).await?;
    Ok(())
}
```

## 8. Config Paths per OS

```rust
// crates/zeroclaw-config/src/paths.rs
use directories::ProjectDirs;

pub fn config_dir() -> PathBuf {
    ProjectDirs::from("com", "zeroclaw-labs", "zeroclaw")
        .map(|d| d.config_dir().to_path_buf())
        .unwrap_or_else(|| PathBuf::from(".zeroclaw"))
}
```

The `directories` crate provides the OS-appropriate config directory:
- macOS: `~/Library/Application Support/zeroclaw/`
- Linux: `~/.config/zeroclaw/` (respects `$XDG_CONFIG_HOME`)
- Windows: `%APPDATA%\zeroclaw\`

```toml
# Cargo.toml
directories = "6.0"   # cross-platform config/data/cache dirs
```

## 9. TOML Edit — Preserving Comments

When the config is saved back to disk after patching, user-written comments
must be preserved:

```toml
# config.toml
[agent]
# This is my favourite model
model = "claude-opus-4-5"
```

If we serialised the `Config` struct with `toml::to_string()`, the comment
would be lost. Instead, the project uses `toml_edit`:

```rust
// crates/zeroclaw-config/src/comment_writer.rs
use toml_edit::{Document, Item};

pub async fn apply_comments(
    path: &Path,
    comments: &[(String, String)],  // (toml_key_path, comment_text)
) -> anyhow::Result<()> {
    let content = tokio::fs::read_to_string(path).await?;
    let mut doc = content.parse::<Document>()?;  // parse preserving formatting

    for (key_path, comment) in comments {
        // Navigate to the key and set its decoration
        if let Some(item) = doc.get_item_mut(key_path) {
            item.decor_mut().set_prefix(format!("# {comment}\n"));
        }
    }

    tokio::fs::write(path, doc.to_string()).await?;
    Ok(())
}
```

`toml_edit` represents the TOML document as a *lossless* AST — comments,
whitespace, and ordering are all preserved. Changes are applied surgically
to specific nodes.

```toml
# Cargo.toml
toml = "1.0"           # for parsing/deserialising into Config struct
toml_edit = "0.25"     # for lossless editing preserving comments
```

## 10. The `schemars` JSON Schema Export

```rust
// crates/zeroclaw-config/src/schema.rs
use schemars::JsonSchema;

#[derive(JsonSchema)]
pub struct Config { ... }
```

`schemars` derives a JSON Schema from the `Config` struct. This is used by:
- The web dashboard to generate dynamic config edit forms
- The CLI `zeroclaw config schema` command
- IDE integrations (JSON Schema → TOML autocomplete)

```toml
# Cargo.toml
schemars = "1.2"
```

The generated schema includes field descriptions (from doc comments), types,
required/optional status, and validation constraints — everything a UI or
validator needs without maintaining a separate schema file.
